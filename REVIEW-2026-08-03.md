# Overview and improvement suggestions — 2026-08-03

> **A snapshot, not a queue.** Dated in the filename on purpose: the moment anything
> here is adopted it becomes a GitHub issue, which is where this repository tracks
> work that can be closed. Nothing below restates a count that a file already holds
> and a test already checks — where a number appears it is a measurement taken today,
> with the command that produced it.
>
> Every item was checked against the working tree, not recalled. Where a suggestion
> conflicts with something the README argues for on purpose, the conflict is named.

## 1. Where the project actually is

A static page, no build step, no dependencies. Paste a decklist, get the combos in
it and a ranked list of cards that would unlock more. Combo data is a nightly
snapshot of Commander Spellbook published to the `data` branch.

**Measured today:**

| | |
|---|---|
| Unit tests | **607** passing, ~2s (`npm test`) |
| Coverage | **96.09%** lines / 92.46% branch / **96.00%** functions, against floors of 94/90/95 |
| Browser payload | **142 KB gzipped** across 11 scripts + CSS + HTML |
| Published data | 1.28 MB on the wire, 103,747 combos (`tools/substitution-scope.js`) |
| Unofficial rows | 235 hand-written rows, 1 stand-in rule (`npm run check:readme`) |
| Open issues | **0** |
| Open PRs | **0** (Dependabot's three action bumps are merged; workflows are on `@v7`) |
| Docs | README 196 KB, CLAUDE.md 25 KB, IMPROVEMENTS.md 31 KB (history) |

**The backlog is empty.** All ten technical items from the original review are
settled, nine features remain unbuilt, and there is no open issue. So this is
genuinely a "what next" moment rather than a triage one.

### What is in unusually good shape

Worth saying, because it changes which suggestions are worth making:

- **The payload work is done and was decided by measurement.** Two substantial ideas
  (sharding the download, keeping a decoded copy in IndexedDB) were closed by a
  61 ms parse reading off a real phone. That instrument — the footer line — is the
  best thing in the repository.
- **The deploy cannot ship an unstamped asset.** `tools/stamp-assets.js` reads what
  the page references rather than a list, so adding a `<script>` is free. Several
  suggestions below are cheap *because* of this.
- **The unofficial list maintains itself.** Citations are verified nightly against
  the snapshot; a row Spellbook has since published goes into a self-rewriting issue.
- **Prose numbers are checked in CI** (`npm run check:readme`, 8 claims).
- **Research passes cannot be faked.** `research-log.js` rejects a pass without
  verbatim oracle text, which is the rule that caught two mis-read cards.

### T-A — Exercise the fetcher in CI *(M, highest value)*

`tools/fetch-combos.js` measures **59.08% lines / 51.43% functions** — by a wide
margin the least-covered code here, and the uncovered lines are the fetch, shape and
publish paths (238-344, 506-604, 648-782). It is also the only code in the repository
that force-pushes a branch, unattended, at 04:17 UTC.

Everything downstream of it is well guarded: `check-snapshot.js` has 351 lines of
tests, the publish gate checks four counts and every row's shape, `--steps` walks
every file against `StepsSource.pathFor()`. The gate is good. What is untested is the
code that produces the thing the gate inspects.

**Proposal:** a `--fixture <file>` mode that replays a small canned export (twenty
variants, including the awkward shapes — a template slot, a missing id, a card the
name table has to intern) through the real fetcher, and a CI step that asserts the
output decodes to the twenty combos with their ids rebuilt. No network, a second to
run, and it closes the last critical path nothing exercises.

**What it trades:** a fixture is a shape somebody else controls, frozen. That is
exactly what `peek-variant.yml` exists to re-check, so the two go together — the
fixture needs a comment saying which run of that workflow it was taken from.

### T-B — Split `app.js` *(M, mechanical)*

93 KB, 2,078 lines, ~60 functions, and by design the one shipped file `node --test`
cannot reach. T4 already pulled the *decisions* out into `view-model.js`; what is left
is rendering, and it keeps growing. `renderGraph()` alone is roughly 290 lines
(app.js:1018–1308) — the map's DOM half is larger than most modules in the repo.

**Proposal:** cut along the seams the file already has as comment banners, into
DOM-only siblings loaded in order — `render-combos.js`, `render-map.js`,
`render-suggestions.js`, `deck-io.js` — leaving `app.js` as wiring. The invariant
("only these files touch the DOM of `index.html`") is preserved; what changes is that
a diff to the map no longer sits in the same file as the file-drop handler.

**Why it is cheap here specifically:** the deploy derives its own asset list, so
adding four scripts costs four `<script>` tags and nothing else. `tools/verify-layout.js`
builds its fixture from the same `rewriteAssets()`, so it follows automatically.

**What it trades:** four more requests on a cold load. If that matters, the same cut
works with the four concatenated at deploy — but do not do that without a number,
which is this repo's own rule.

### T-C — Load the in-page fallback lazily *(S)*

`index.html` loads eleven scripts. Four of them — `result-tiers.js`, `combos.js`,
`unofficial.js`, `search.js` — exist in the page *only* so a browser without `Worker`
still has a way through. That is **64 KB of the 142 KB gzipped shell**, and it parses
and allocates on the main thread on every single load. Measured under Node, the four
cost ~13 ms and build the 235-row table twice, once here and once in the worker.

Be precise about the win, because it is not bytes: the worker fetches the same URLs, so
the HTTP cache already means one download. What lazy loading buys is **taking 64 KB of
parse and heap off the critical path** — the worker does it off-thread, in parallel with
first paint, instead of the window doing it first and the worker doing it again.

**Proposal:** in `startWorker()`'s failure path and the `typeof Worker !== 'function'`
branch, inject the four scripts and await them before `inPageSearch()`.

**The fallback is not a branch nobody executes** — `tools/verify-layout.js` renders one
viewport with `Worker` deleted, so the *behaviour* is already covered.

**But the stamping of it is not, and that was checked after this was first written.**
`VIEWPORTS` has `desktop (no worker)`, which runs unstamped, and
`desktop (asset-stamped)`, which asserts the search went through the *worker*. No
viewport is both. Today that is harmless — the four scripts are in the HTML, so the
deploy's rewrite stamps them and the no-`Worker` page gets stamped copies for free. The
moment they are injected from `app.js`, nothing covers whether they carry the stamp, on
a path that only runs for readers whose worker has already failed. An unstamped URL
resolves fine and serves whatever the CDN cached, which is exactly how `unofficial.js`,
`graph.js` and `theme.js` each shipped stale.

So this needs **one new viewport** — stamped *and* worker-less — which makes it a small
S rather than a free one. `tools/stamp-assets.js` itself needs no change: it only
inspects `src=`/`href=` in the HTML and asserts nothing *referenced* is left bare, so a
script that leaves the page is simply not its business. `search-worker.js` is the
standing precedent. `stampedIndex()`'s `n >= 6` guard also survives: 13 referenced
assets today, 9 after.

**What it trades:** the README currently says "the same code either way — `search.js` is
loaded both ways rather than duplicated", and that sentence stays true; what stops being
true is "loaded unconditionally". Also the stamp then travels **three** hops that no
`sed` can reach rather than two, which the `VIEWPORTS` comment states explicitly.

### T-D — A wire-size ceiling in the publish gate *(S)*

Interning and dropping the id took the payload 2.73 MB → 1.28 MB, and the download is
still 94% of a cold search. Nothing prevents that regressing: the gate checks counts and
row shapes, not size. One new field in Spellbook's export, kept by a future
`compact()`, would put it back with every check green.

**Proposal:** the gate already has the published blob in hand — fail if its gzipped size
exceeds a ceiling (say 1.6 MB), with the ceiling in the workflow beside a comment saying
what today's reading is. Same idea as the coverage floors: set a little above current, so
it catches a shape change rather than bickering over kilobytes.

### T-E — Cover the cache branches in `search.js` *(S)*

`search.js` is the weakest shipped module: **87.50% functions, 75.34% branches**, and
the uncovered lines (105-106, 120-121, 138-139, 153-154, 168-173, 190-191) are exactly
the Cache Storage paths — open, match, put, the deadline race, the tidy-up of old
versions.

Those branches are deliberately allowed to fail silently, which is right, and it is also
what makes them worth testing: a caching layer that has quietly stopped working looks
identical to one that is working, except every visit pays 1.5 s. The second-visit reading
in the README (`cache 39ms`) is the only evidence it works, and it was collected by hand
on a phone.

**Proposal:** a fake `caches` object in the tests — twenty lines, no DOM — asserting the
four behaviours that matter: a hit is served, a miss is stored, a bumped `CACHE_NAME`
abandons the old copy, and a cache that never resolves is treated as absent after the
deadline. That last one is a real bug this code was written to survive (headless Chrome
on a virtual clock) and nothing regression-guards it.

Also note the functions margin is **exactly 1.00 point** above the floor (96.00 vs 95).
The next module that arrives lightly tested breaks the build — which is the design
working, but worth knowing before it happens on an unrelated PR.

### T-F — A service worker for the shell *(S)*

Today the *data* survives going offline (Cache Storage, 1.28 MB) and the *page* does
not: plane mode fails on `index.html`. For a tool you would plausibly use at a table
with bad wifi, that is the wrong way round.

**Why this repo is unusually well-placed:** the classic service-worker failure is
shipping an update nobody receives. `?v=<sha>` stamping already makes every asset URL
immutable and every deploy a fresh set of URLs, so a cache-first SW over stamped URLs
cannot serve a stale mix — the exact hazard is already engineered away. CSP needs no
change (`worker-src 'self'` is already there).

**What it trades:** `index.html` itself is not stamped (deliberately — it must stay
cacheable-but-fresh), so the SW has to be network-first for the HTML and cache-first for
everything else. That asymmetry needs writing down or somebody will "simplify" it.

### T-G — Commit an oracle-text cache from a runner *(M)*

The research loop's binding constraint is not finding candidates — `substitution-scope.js`
prints 4,835 implied unpublished combos and a ranked queue on demand. It is that
**`research-log.js` requires verbatim oracle text**, and the sandbox this repo is edited
from cannot reach Scryfall, so passes fall back to Forge's wording under a banner and
"cross-check against XMage" becomes a manual step per card.

Right now `lookup.yml` prints text into a run summary, where it is read once and lost.

**Proposal:** a workflow that takes the top N of the queue (or an explicit list), fetches
real Scryfall oracle text on a runner, and commits it to a `card-text.json` cache on a
branch. `tools/lookup-card.js` reads that first, Scryfall second, Forge third. Sandbox
passes then get Scryfall's exact wording with no caveat, and the cache is a diff somebody
can review.

**What it trades:** a cached card text can go stale on an oracle update (rare, but real
— errata happen). Store the fetch date per card and have the tool say how old it is,
which is the same honesty the Forge banner already practises.

**Why it is worth the M:** 866 of the cards in interchangeable pairs have no recorded
pass. That queue is not getting shorter by making each pass more expensive.

### T-H — Decide the `unofficial.js` threshold now *(S, mostly a decision)*

`unofficial.js` is **285 KB raw / 28.7 KB gzipped** — the largest single script in the
shell — and it is data: 235 rows and one rule. It grows every time somebody does a
research pass, and never shrinks except by graduation.

It should stay in the repo for now: rows are versioned with the code, `verify:unofficial`
is a repo test, and 28.7 KB is not a problem. But the trend is monotonic and the decision
is easier made cold.

**Proposal:** write the threshold down (e.g. "at 50 KB gzipped, move `COMBOS` to the
`data` branch as JSON, fetched by the worker only"). `connect-src` already allows the
host and Cache Storage already exists, so the move is small; what it costs is that rows
stop being versioned with the code and `verify:unofficial` becomes a publish gate rather
than a test. That is a real trade and worth deciding once, in advance, rather than under
pressure.

### T-I — Two stale numbers *(XS)*

- `CLAUDE.md:19` says the suite is **590 tests**. It is **607**. `check:readme` anchors
  on the README only, so nothing catches this — either extend it to CLAUDE.md's countable
  claims or drop the number and say "fast".
- `IMPROVEMENTS.md`'s "Not verified" section says the second-visit measurement is still
  missing. The README now carries it (`ready in 0.2s (cache 39ms · parse 43ms · match 71ms)`).
  IMPROVEMENTS is history, so a one-line "since answered, see README" is enough — but two
  documents currently disagree about whether the caching design has been proven.

### F1 — "Why isn't X a combo with Y?" in the page *(M)*

Unchanged and still the recommendation. `tools/combos-with.js` answers the question
players actually ask and is available only to someone with a checkout and a terminal.
The worker is already holding the whole database in memory by the time anyone would ask.
Two card-name boxes and an answer that separates *Spellbook does not list this* from
*Spellbook lists it and your deck is two cards short* is a new capability built almost
entirely from logic that exists, over data already downloaded.

It also fits the page's voice, which is the real argument: every panel here explains why
a result is what it is instead of asserting it.

### F6 — Export the answer *(S, best value per line of code)*

**Copy link** shares the input. Nothing shares the output. One function over the result
object already in hand, onto the clipboard as markdown, and the answer goes into a
Discord message or the deck's own description field.

`view-model.js` is the right home for the formatting — it is where a sentence's wording
already lives, and it is the half `node --test` can reach.

### F2 — Cut candidates *(S)*

The page ranks cards to add and never names one to remove, although `comboPieces()`
already builds the card → combos index that answers it: the deck cards *absent* from
that index appear in no combo, no near-miss, and fill no template slot.

Note this is **not** the shipped "cards carrying your combos" panel, which ranks the
cards that do appear. F2 is its complement, and the complement is the one that helps
when trimming.

The framing has to be careful and the README is already good at this: a card earns its
slot without being combo-relevant all the time, and a tool that says "cut your removal"
is not trusted twice. *"These cards are not part of any line this page can see"* is both
honest and useful.

### N1 — Say what changed after **+ Add to deck** *(S, new)*

Pressing **+ Add to deck** re-runs the search and redraws everything, including the map.
What it never says is what the card did. The reader watches a page change and has to
diff it by eye — after pressing a button whose entire promise was a number.

*"Sol Ring added — 4 new combos, 2 new suggestions"* is a diff of two result objects the
page has both of. It is also the cheap half of F9, so building it first makes F9 smaller.

### F10 — Filter the map by tier *(S)*

The map filters by *relation* (works-together vs interchangeable) and colours lines by
tier. It cannot filter by tier. On a 28-card, 114-line map, *"show only the lines that
end the game"* is the view most people want, and the data and CSS classes both exist —
one more entry in `MAP_VIEWS`, one more class on the SVG.

### N2 — "It's in your sideboard" *(S, new)*

The parser deliberately ignores the sideboard when counting combos, and the README argues
that well. But a *suggestion* is a different question: telling somebody to acquire a card
they already own, parked in their maybeboard, is the kind of miss that makes a tool feel
careless.

`parseDecklist()` currently returns `{ commanders, main, skipped }` — sideboard cards are
discarded rather than reported, so this needs one small change there before the panel can
say anything. Nothing about the combo counting changes: the card is still not in the
deck. It just stops being presented as a purchase.

### F5 — Legality alongside the bracket *(S)*

Two questions come nearly free from machinery that exists: **cards outside the deck's own
colour identity** (`withinIdentity()` is written) and **banned cards** (a short list, a
few changes a year, fetchable in the same nightly job that already reads identities off
Scryfall). Both fit the bracket panel's established shape — a claim made only where the
decklist supports it, explicit about what it did not check.

### F8 — Remember more than one deck *(S)*

`localStorage` holds one decklist under one key. Most players have several decks, and the
encoding needed to store more is already written for the share link. A short list of
named, restorable recent decks is a small change against existing machinery.

### N3 — Two-card packages, not just one card away *(M, new)*

Suggestions are strictly one card away. The natural next question — *"what three cards
should I buy?"* — is not the top three of that list, because those three often unlock
overlapping combos, and because some of the best packages are pairs where neither card
does anything alone.

The full version is combinatorial and not worth it. The honest cheap version: consider
only pairs drawn from cards **already suggested individually**, score by combos unlocked
together, and show the top few as *"these two together unlock 7"*. Bounded, and it uses
the near-miss data already computed.

### F9 — Compare two decks *(M)*

`matchAgainst()` is a pure function of dataset and entries, so running it twice and
diffing gives *combos gained / combos lost* for free. Smaller if N1 lands first, since N1
is the same diff over one deck at two moments.

### F3 — Prices on the suggestions *(M)*

Ranked by combos unlocked, with no notion of cost — which is the second question every
reader has and often the deciding one. The README names MTG-Pricerunner as the sibling
project doing this publish-as-data trick already, same author, so the pattern and the
source both exist. *"Show me what £20 unlocks"* turns a ranked list into a decision.
Costs a `connect-src` entry, or a join in the nightly job.

## 4. Settled — please do not reopen

Recorded so a future review does not re-derive them:

| | |
|---|---|
| Sharding the payload (T2) | closed by measurement: the download is a *cold* cost the cache already handles |
| Decoded copy in IndexedDB (T3) | closed: the parse is 61 ms on a real phone |
| Text search over combo descriptions | asked and answered — **not wanted**; the decklist is always the entry point |
| Querying Spellbook's API live | their CORS allowlist forbids it; `setSource()` remains the seam if it changes |
| Range requests into `raw.githubusercontent.com` | Fastly gzips `text/plain`, so ranges address the *compressed* stream |
| More deck-site URL adapters | probed 2 Aug 2026: Deckstats, MTGGoldfish, TappedOut all refuse cross-origin |
| Paging Spellbook's `/variants` | cumulative quota; the bulk export is the only way |

## 5. Still open, and one CI blind spot

**Archidekt — only you can settle this, and it takes ten seconds.** Paste an Archidekt
deck URL into the live page. The evidence that it broke is strong but indirect: asked as
themselves they answer `Access-Control-Allow-Origin: https://archidekt.com`, asked as us
they answer `http://localhost:3000`, and a browser discards a response naming somebody
else. This gates the one deck URL the page advertises, and no suggestion above should be
built on the assumption it works. If it does fail, the fix is one line
(`SITES.archidekt.browserImport = false`) plus a `why` pointing at the file drop, exactly
as Moxfield already does.

**Dependabot's three PRs are done** — `checkout`, `setup-node` and `upload-artifact` are
all on `@v7`, and the README's version section is current, including the finding that
`upload-artifact@v5` had been on the deprecated `node20` runtime all along.

That section names a blind spot worth closing, though, and it is small enough to fold
into T-A's workflow-testing pass: **`ci.yml`'s `upload-artifact` step is behind
`if: failure()`**, so a bump to it is only ever proved by the next red run — which is the
worst possible moment to discover the Playwright report no longer uploads. A
`workflow_dispatch` input that forces that step once (`if: failure() || inputs.prove_upload`)
makes it provable on demand instead of retroactively. **S.**

## 6. If only three get done

1. **T-A** — exercise the fetcher in CI. It is the last untested critical path, and it is
   the one that force-pushes unattended.
2. **F1** — "why isn't X a combo with Y" in the page. The most-asked question, answerable
   from data already in memory, and the best fit for what this page is.
3. **T-C** — lazy fallback. An afternoon plus one new layout viewport, and it takes 45%
   of the shell off the critical path.

**F6** deserves a mention as the cheapest genuinely new thing on the list: one function,
one button, and the answer becomes shareable.
